# Help content — the one source of truth

Every piece of help content for the platform lives here, as markdown, at
`docs/help/<feature>/<role>.md`. The in-app help centre (Phase C), the
assistant's support-mode retrieval corpus (Phase B) and the walkthrough videos
(Phase D) are all generated from these files. There is never a second copy
anywhere — not in Notion, not in a PDF, not in a component's string table.

Brief: `docs/briefs/claude-code-brief-help-content-foundation.md`.

## The rule (also in `CLAUDE.md`)

A feature is not done until its help files exist or are updated for every role
that can see it. Help files **ship in the same PR as the feature**. They are
written **after** the e2e run, from the real screens in the real role, using
`_template.md`. Briefs are background reading only: where a brief and the
running app disagree, the help file follows the app and the discrepancy goes in
the session report.

## Folder convention

```
docs/help/
  README.md                 this file
  _template.md              copy this to start a new help file
  _index.json               GENERATED by scripts/help-index.ts — never hand-edit
  <feature>/
    staff.md                one file per role that can see the feature
    pc.md
    contractor.md
    customer.md
    media/
      <role>-<step>.png     screenshots, e.g. contractor-01.png, contractor-02.png
      <role>-walkthrough.gif  the silent walkthrough GIF (see Walkthroughs)
```

- `<feature>` is a lowercase slug: letters, digits and single hyphens
  (`scheduling`, `self-invoicing`, `work-orders`). It must equal the
  `feature:` value in every file inside it.
- Only role files live directly inside a feature folder. Anything else the
  index script treats as an error, so a typo like `contractors.md` cannot
  ship silently.
- Screenshots and GIFs live in `<feature>/media/` and are referenced with
  relative paths (`media/contractor-01.png`). A reference to a file that does
  not exist fails the index.
- Nothing starting with `_` is indexed (`_template.md`, `_index.json`).

## Roles (the only allowed `role:` values)

| role | who reads it | notes |
|---|---|---|
| `staff` | all office staff | estimating, sending, scheduling, invoicing as seen by the office |
| `pc` | project coordinator | a specialisation of staff. Where a screen is PC-only (PC console, attention queue, variation pricing, remote sign-off gate) write `pc.md`; where it is all office staff write `staff.md`. **Never both for the same content.** |
| `contractor` | painters and their companies | inside the platform only (`/portal`). Never margin, charge-out rates, PC console or customer money |
| `customer` | residential and trade clients | written when the customer portal exits its proving window; served through the assistant, not a route |

Role scoping is **by construction**: each role gets its own file. There is no
shared file with sections hidden per role, and a screenshot in a contractor
file must not show anything a contractor cannot see on their own screen.

## Front-matter spec

```yaml
---
feature: scheduling                      # required — equals the folder name
role: contractor                         # required — one of the four roles; equals the filename
title: Accept, decline or propose a date for a job offer   # required — what the page helps you do
summary: How a job offer reaches you and what happens in the 24 hours after.  # required — one sentence
walkthrough: media/contractor-walkthrough.gif   # optional until session A4; must exist if given
verified_at_commit: 1a2b3c4d             # optional; set by scripts/help-index.ts (session A4)
---
```

Rules for the body (from the brief, §6):

- Write in the second person, imperative steps, one action per step.
- No screenshots or text that reveal content outside the file's role.
- No promises about timing, pricing or policy that are not already a shipped
  Settings value.
- Plain English, English (not Australian) idiom in contractor and customer
  files. Staff files can be internal but still plain.
- Money, where it appears, is AUD including GST.
- State names must match the on-screen label and the enum value exactly.
- Colour words match the design tokens: **amber** = waiting on something,
  **cyan** = confirmed / active, **emerald** = accepted / done,
  **clay** = overdue or needs attention now, **graphite** = not started.

## The index — `npm run help:index`

`scripts/help-index.ts` walks this folder, validates every help file and
writes `_index.json` (feature, role, title, summary, walkthrough, media,
verified_at_commit, path). Phase B reads that index for retrieval, so it is
committed and CI runs `npm run help:index -- --check`, which fails when:

- a role file has missing, unknown or malformed front-matter;
- `role` is outside the allowed set, or does not match the filename;
- `feature` does not match its folder, or is not a slug;
- a referenced screenshot or walkthrough file is missing;
- a stray `.md` sits in a feature folder or at the top level;
- the committed `_index.json` is stale (regenerate and commit it).

Errors print one line each, `path: what is wrong`, and the script exits 1.

## Screenshots — the capture rig

Screenshots are never taken by hand. `e2e/help-capture/<feature>.spec.ts`
drives the real flow in the real roles on the C1 **test** stack (never
production) and saves `docs/help/<feature>/media/<role>-<step>.png` as it goes:
contractor shots at a 390×844 phone viewport, staff shots at 1440×900. The
fixtures are invented test data (`rig.ts`), created before the run and
destroyed after it. When a screen changes, re-run the spec and re-read the
help file against the new pictures:

```bash
./scripts/c1/run-e2e.sh e2e/help-capture/scheduling.spec.ts
./scripts/c1/run-e2e.sh e2e/help-capture/self-invoicing.spec.ts
./scripts/c1/run-e2e.sh e2e/help-capture/work-orders.spec.ts
```

These specs are not CI gates — they exist to regenerate the media. They share
the C1 test contractor with the real e2e suites, so run them when nothing
else is driving that stack, and expect the console screenshots to show the
volume-test jobs C1 carries. Photos they upload are generated placeholders
(`placeholderPng` in `rig.ts`); no real site photo is ever committed.
