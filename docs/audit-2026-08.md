# Engineering audit — August 2026

Audited against `CLAUDE.md`. **No fixes applied** — findings only.

Method: static analysis of the repo plus live testing against the Supabase
project (`llmrvgdequpmzzuaxdhq`) using four identities — staff, two different
contractors, a customer, and an anonymous client. Where a claim could be tested
rather than reasoned about, it was tested.

**Three findings were withdrawn during the audit** because a first-pass grep was
wrong (see *Corrections* at the end). Nothing below is asserted from a pattern
match alone.

# CRITICAL

### C1 · Money is written by the browser and never recomputed server-side
**`app/(app)/schedule/ScheduleBoard.tsx:427,465` · `app/quote/OfferPanel.tsx:118`**

When staff drag a job onto the board, the browser supplies `payment_cents` for
the booking offer. `CLAUDE.md`: *"Never trust client-computed totals — recompute
server-side."*

Anyone who can reach the staff UI can offer a job at any amount by editing the
request in devtools. The offer is what the contractor accepts and later invoices
against, so this is the money path, not a display value.

**Fix:** an RPC that takes `(work_order_id, contractor_id, start, end)` and
derives the payment from the work order server-side; the client never sends an
amount. **Size: M**

### C2 · Multi-step booking operations are sequential client calls
**`ScheduleBoard.tsx:420-430` (send), `:459-470` (reassign), `:475` (move)**

Sending an offer is *update work_orders* then *insert booking_offers*.
Reassigning is *cancel* → *update* → *insert*. `CLAUDE.md` requires one Postgres
transaction via RPC.

If the second call fails — dropped connection, closed laptop — the job is left
assigned to a contractor with no offer, invisible to both sides. Half-written
state in the booking system is how a customer ends up with nobody arriving.

**Fix:** fold each into one `security definer` RPC. Combine with C1 — same
functions. **Size: M**

### C3 · State columns are set directly from routes
**`ScheduleBoard.tsx` (work_orders.status/contractor_id/start_date),
`OfferPanel.tsx:143` (booking_offers.state = 'withdrawn'),
`QuoteBuilder.tsx:642` (estimates.status = 'sent'), `:984` (work order issue)**

`CLAUDE.md`: *"transitions changed only through dedicated server functions that
validate the current state. No route sets a status column directly."*

The contractor-side transitions are correct (`respond_to_offer`,
`cancel_booking`, `resolve_proposed_offer` all validate). The staff side bypasses
them, so nothing stops an offer being withdrawn after it was accepted, or a job
being moved to a contractor who is suspended, from a stale tab.

**Fix:** `withdraw_offer`, `issue_work_order`, `send_estimate` RPCs that check
the current state before writing. **Size: M**

### C4 · No input validation anywhere
**Whole app — only `lib/presentations/schema.ts` imports zod**

There are **zero API route handlers** and **one** server action file
(`app/auth/actions.ts`, unvalidated). All 58 mutations go browser → PostgREST
directly, so there is no server boundary at which validation could happen.

RLS limits *which rows* a user touches; it does not validate *what they write*.
A contractor can set `crew_size` to 99, an invite to expire in 3650 days, a
document's `expires_on` to 2099 — all within policy.

**Fix:** this is the same shape as C1–C3. Route the mutations that matter
(money, state, compliance) through validated server functions; leave benign
profile edits on PostgREST. **Size: L overall, but M if scoped to money+state.**

### C5 · File uploads are not validated server-side
**`ProfileForm.tsx` (insurance, logo), `ProductsManager.tsx`, `PresentationsManager.tsx`**

Uploads go straight from the browser to Supabase Storage. The only constraint is
the `accept=` attribute on the file input, which is a UI hint, not a control. No
MIME check, no size limit, on any of the 6 upload paths.

A contractor can upload a 2 GB file, or an HTML file as their "certificate".
Storage policies correctly scope *where* they can write; nothing checks *what*.

**Fix:** size/MIME check before upload plus a storage-level constraint; ideally
a server action that validates then issues a signed upload URL. **Size: M**

# SHOULD FIX

### S1 · Contractor pay exists in three places with nothing keeping them equal
**`work_orders.contractor_payment_cents`, `wo_snapshot.contractorPaymentCents`,
`booking_offers.payment_cents`**

All three are written by client code and no constraint relates them. Today they
agree on real records only because the same code path wrote all three.

*(One divergent row exists — `WO-OVERLAP2`, snapshot 160139 vs column 90000 —
but that is fabricated audit test data, not an organic failure. The structural
risk is real regardless.)*

**Fix:** make the offer the single source of truth, or derive both others from
it in the RPC from C1. **Size: S** once C1 exists.

### S2 · `/join/[token]` returns 200 on an unknown token
**`app/join/[token]/page.tsx`**

`CLAUDE.md` requires 404. `/e/[token]` and `/w/[token]` both correctly `notFound()`;
join renders a friendly "this link isn't valid" page with a 200.

The friendly page is better UX for an *expired* invite. For a token that has
never existed it is an oracle: it confirms the difference between "no such
token" and "revoked".

**Fix:** 404 for not-found; keep the friendly page for expired/revoked/used.
**Size: S**

### S3 · No rate limiting on any token route
**`/e/[token]`, `/w/[token]`, `/join/[token]`**

Explicitly required. Entropy is high enough that brute force is impractical
(below), so this is defence in depth rather than an open door — but it is
absent, and these are the only unauthenticated routes in the app. **Size: S**

### S4 · Missing index on `work_orders.contractor_id`
**`supabase/migrations/` — no index declared**

Filtered on every portal Jobs load (`lib/contractor/jobs.ts:100,113`) *and*
inside the RLS policy (`20260825000000:35,46`), so it is evaluated on every
contractor row read. Every other FK/filter column checked has one.

**Fix:** `create index on public.work_orders (contractor_id);` **Size: S**

### S5 · Two screens fire far more than ~5 queries
**`app/quote/page.tsx` ≈ 13 + 2 (layout) · `app/(app)/settings/page.tsx` ≈ 11 + 2**

Both load the full reference set (rate items, modifiers, products, settings,
line items, area names, colours, presentations…) on every render. The rule asks
for one round trip per screen where possible.

Also: **the portal runs its session guard twice per request** — the layout calls
`getContractorSession()` and the page calls `requireContractor()`, each doing
getUser + profiles + contractors. That is 3 redundant queries on every portal
page.

**Fix:** one RPC returning the reference bundle for the builder; `cache()` the
session guard per request. **Size: M**

### S6 · Unbounded selects on tables that grow
**`lib/scheduling/board.ts:122` (all booking offers), `app/(app)/contractors/page.tsx:20`
(all offers), `app/quote/page.tsx:56` (all products), `app/(app)/settings/page.tsx:28,33`**

No `.limit()` or `.range()`. Fine at today's volumes (8 offers, 40 products);
`board.ts` in particular fetches *every offer ever made* on each board load.
**Fix:** date-window the board query; paginate products/estimates. **Size: S–M**

### S7 · Pricing math lives in the component, not `lib/pricing/`
**`app/quote/QuoteBuilder.tsx` — `surfaceCalc`, `totals`, `computeWorkOrderDoc`**

`CLAUDE.md`: *"Estimate pricing math lives in ONE module. No component computes
prices independently."* QuoteBuilder imports only `hoursPerUnit` from the engine
and does the rest itself (~200 lines of pricing inside a 2,500-line client
component).

Consequence beyond tidiness: the pricing cannot be called server-side, which is
*why* C1 exists — the server has no way to recompute an amount. Fixing this
properly unblocks C1 permanently.

**Fix:** extract surface/line/total calculation into `lib/pricing/estimate.ts`,
imported by both the builder and the RPCs. **Size: L** — and the highest-value
refactor in this list.

### S8 · No tests for anything built in the last five phases
**`package.json` — `node --test` on the pricing engine only; no vitest, no playwright**

12/12 existing tests pass, but they cover the original engine. The offer state
machine, expiry, the privacy gate, compliance verification, cancellation and
reschedule all have **zero** automated coverage. Every one was verified by hand
against the live database — which found real bugs, but none of it is repeatable
and nothing guards against regression.

`CLAUDE.md` names Vitest and Playwright specifically; neither is installed.

**Fix:** Vitest for the offer state machine and money math (pure functions,
cheap); one Playwright smoke test for offer → accept. **Size: M**

### S9 · No error monitoring; 9 silent catches
**`ScheduleBoard`, `OfferPanel`, `QuoteBuilder:309,370,995`, `CustomerEstimate:88,111`,
`w/[token]/page.tsx:20`, `board.ts:106`**

No Sentry. Nine `catch {}` / `.then(() => {}, () => {})` swallow failures. Most
are deliberately best-effort (view tracking, expiry sweeps) but three are not:
`QuoteBuilder:309` and `:370` silently drop work-order and product writes, and
`CustomerEstimate:111` silently drops the customer's **signature**.

**Fix:** Sentry, then triage each catch — best-effort ones log and continue, the
three above surface to the user. **Size: M**

### S10 · Bank detail changes raise no staff alert
**`contractor_set_bank` RPC**

Encrypted at rest ✓, masked in display ✓, alert on change ✗. Bank-detail changes
are the classic invoice-redirection fraud vector, and this is the one control of
the three that is missing.

`contractor_events` already records a `bank_changed` row — nothing surfaces it.
**Fix:** show unreviewed bank changes on the Contractors page. **Size: S**

# Verified as compliant

Worth recording so these aren't re-litigated:

- **RLS**: all 39 tables have RLS enabled *and* at least one policy. Tested live:
  anonymous reads **nothing** from any table; contractor A sees only their own
  rows (4/8 booking offers, 1/4 contractors, 10/11 unavailability); contractor B
  sees none of A's; the customer sees only their own estimate and profile.
  *12 tables are empty, so isolation there is untested rather than proven.*
- **Service-role key**: referenced only in `scripts/*.ts` (Node, never bundled).
  Not in `.env.local`, not in `.next/static`. The app runs entirely on the anon
  key + RLS.
- **Contractor HTML**: fetched `/w/<token>` and stripped script/style content —
  the only visible money is the contractor's own `$1,601.39`. Customer total
  ($9,800) absent; no margin, no subtotal, no email addresses. Earlier apparent
  hits were CSS `margin:` and minified script content.
- **Integer cents**: 14 `*_cents` columns; no float/numeric money columns. The
  only `numeric` columns are hours, coverage, multipliers and dimensions.
- **Token entropy**: estimates 28 chars base62 (~166 bits, `crypto.getRandomValues`);
  work orders 64 hex (~256 bits); invites 48 hex from `gen_random_bytes(24)`
  (~192 bits). All well above the ≥24-char rule. No sequential IDs in any token
  URL.
- **Unknown tokens**: `/e/` and `/w/` both 404 correctly.
- **Typecheck**: clean. **Lint**: 0 errors, 2 warnings, both pre-existing and
  unrelated. **Tests**: 12/12 pass. **`any`**: zero occurrences; `strict: true`.
- **Schema drift**: every column declared across 20 migrations exists live, and
  every live column is declared. Zero drift in both directions.
- **Snapshots**: `/e/[token]` and `/w/[token]` both render stored snapshots via
  security-definer RPCs, never live drafts. Staff now read the same snapshot.

# Corrections made during this audit

Recorded because they nearly became false findings:

1. **"7 tables have RLS but no policies"** — wrong. The initial schema pads
   policy declarations with multiple spaces; a single-space regex missed them.
   All 39 tables have policies.
2. **"`contractor_unavailability.contractor_id` has no index"** — wrong. The
   index definition wraps across two lines and a one-line grep missed it.
3. **"`booking_offers.approval_due_at` and `colour_rules.undercoat` are schema
   drift"** — wrong. Both are declared; the parser mishandled multi-column
   `ALTER TABLE` and a drop-then-re-add sequence.

Every finding above was confirmed by reading the source or by a live query.
