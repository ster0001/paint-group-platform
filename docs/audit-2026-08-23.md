# Workflow audit — 23 August 2026

Scope: the job workflow end to end — schedule → offer → work order → ticks →
variations → QA → completion prep → walkthrough → sign-off — plus the Projects
console, the contractor portal and the estimate delete/settings surfaces around
them. Audited against `CLAUDE.md`.

Method: static reading of every module in the workflow, plus live queries
against the Supabase project to check what the tables actually contain rather
than what the code implies. Where a claim could be tested rather than reasoned
about, it was tested. Findings are marked **fixed today** where the fix was safe
enough to make in the same pass.

# SHOULD FIX

### S0 · A customer can be locked out of the wizard, and it says "Uploading…"
**`app/wizard/WizardApp.tsx:97-106, 472, 537`**

A customer needs an anonymous Supabase session before they can upload or submit.
The effect that creates it does this:

```ts
const { error: signInError } = await supabase.auth.signInAnonymously();
if (!signInError) setSessionReady(true);
else setError("The estimate wizard isn't available just now…");
```

If that call fails, `sessionReady` stays false **for ever** — there is no retry
and no way for the customer to ask again short of reloading. If it never
settles at all (a stalled request on a phone, which the capture code itself
calls "the NORMAL case on site"), not even the error appears: `fetch` has no
timeout, so the promise simply never resolves.

Either way the Continue button is `disabled={uploading || !sessionReady}`, and
page 1 passes `uploading={uploading || !sessionReady}` down — so the button
renders **"Uploading…"** when nothing is uploading. The customer sees a form
that claims to be busy with a file they never chose, and no way forward.

Found by the e2e suite: after enough runs, Supabase rate-limits anonymous
sign-ins and the wizard hangs exactly like this (see S7 — 638 anonymous users
on the live project). A rate limit is a plausible production event too.

**Fix:** retry the sign-in on failure with a visible "try again"; put a timeout
on it so a stall becomes an error rather than a spinner; and never label a
disabled Continue "Uploading…" when the reason is the session. **Size: S**

### S1 · The loop writes invoices nobody can read
**`app/(app)/invoices/page.tsx` · `accept_estimate` · `wo_customer_signoff`**

Accepting an estimate inserts a deposit invoice. Signing off inserts a second
"stub for the invoicing phase to consume". Both are real rows in `invoices`.
The Invoices page is a placeholder that says invoices are "coming next".

Live count: **37 invoices**, none of them visible anywhere in the app.

The workflow therefore has no last step. Everything from estimate to sign-off is
built, instrumented and tested; getting paid is a dead end, and the rows piling
up are the evidence. **Size: M** for a read-only list (staff), **L** with
payments and the customer side.

### S2 · `invoices.customer_id` is never set, so the customer policy can never match
**`20260813000000_initial_schema.sql:564`**

```sql
create policy invoices_customer_select on public.invoices
  for select to authenticated using (customer_id = public.current_customer_id());
```

Every insert in the codebase supplies `estimate_id`, `status`, `amount_cents`
and `issued_on` — never `customer_id`. Live: **37 of 37 rows have a null
customer**. The policy is correct and unreachable: a customer will see nothing
even after S1 is built, and it will look like an RLS bug rather than a missing
column write.

**Fix:** set `customer_id` from the estimate at insert time (all three inserts),
or make the policy read through `estimate_id` the way the work-order policies
read through their job. Do it before the invoices UI exists, not after. **Size: S**

### S3 · The invoice FK contradicts the delete guard
**`20260815000000_customer_view.sql:28`**

`delete_estimate` refuses with `has_invoice` — "deleting it would leave the
invoice with nothing behind it". But the column is
`estimate_id ... on delete set null`, so any delete that does not go through
that RPC orphans the invoice instead of being refused.

Live: **34 of 37 invoices have no estimate and a zero amount** — debris from the
e2e fixtures, which delete their estimates with the service key and bypass the
guard. Production deletes go through the RPC, so this is not currently losing
customer records; the point is that the schema and the app disagree about what
should happen, and the schema is the last line of defence.

**Fix:** `on delete cascade` (an invoice for an estimate that no longer exists
is meaningless) or `on delete restrict` (make the database state the refusal the
app already gives). Then clear the 34 orphans. **Size: S**

### S4 · Painters cannot see the photos they took
**`app/portal/jobs/[id]/SitePhotos.tsx` · `app/pc/wo/[id]/as-contractor/page.tsx`**

`SitePhotos` uploads and counts ("3 sent"); it never lists. The portal job page
reads `wo_photos` only to answer "has this elevation got its before photo?".
So the painter building the record cannot review it, cannot see whether a shot
landed, and cannot check what they already sent before sending it again.

Staff got a gallery on 22 Aug. The painter's own view and the office's mirror of
it did not, which now makes the two views disagree about what exists.

**Fix:** `PhotoGrid` and `lib/workorder/photos.ts` already do this and are
shared-safe; the portal page needs the same signed read the console page uses.
**Size: S**

### S5 · The board reads every work order ever, snapshot and all
**`lib/scheduling/board.ts:119`**

```ts
supabase.from("work_orders")
  .select("id, estimate_id, wo_ref, status, contractor_id, start_date,
           contractor_payment_cents, wo_snapshot, issued_at, estimates ( title )"),
```

No filter. `wo_snapshot` is the whole contractor job sheet — materials, areas,
every surface, exclusions — tens of KB per row, and the board loads it for every
job that has ever existed to read `jobTitle`, `finishCode`, `jobAddress` and a
sum of surface hours.

At four work orders this is invisible. At five hundred it is the slowest screen
in the app, and it is the screen staff keep open all day.

**Fix, in order of effort:** filter out closed jobs; then store the tray's two
derived numbers (total hours, job title) on `work_orders` at issue time so the
board never needs the document at all. **Size: S then M**

**Related, fixed today:** the console was reading every `wo_signoff` row ever
written on every load. `buildQueue` skips signed rows on the first line of its
loop, so `.is("signed_at", null)` changes nothing on screen and stops the read
growing with every job the company ever finishes. The same pass replaced an
O(n·m) `.find()` in the tick-count loop with a Map.

### S6 · The scheduling board has no unit test
**`lib/scheduling/board.ts` — 305 lines, 0 tests**

It derives the unscheduled tray, decides which offers become blocks, lays blocks
into rows without overlapping, converts hours into days, and truncates a suburb
out of an address. All of it is pure logic over its inputs, and none of it is
covered — while `lib/workorder` has eleven test files beside it.

This is the module where a quiet mistake shows up as a job that simply is not on
the board, which is the failure nobody notices until a contractor does not turn
up. **Size: S** — the functions are already shaped for it.

### S7 · The e2e suite runs against production and leaves permanent debris
**`playwright.config.ts` · `e2e/customer-journey/drive.ts`**

There is no local database, so the suite drives the live Supabase project. Every
customer-journey test signs in a fresh anonymous user and completes a real
estimate; nothing cleans up afterwards.

Live, right now:

| | |
|---|---|
| Users on the project | 648 |
| …that are anonymous test users | **638** (98%) |
| Estimates | 70 |
| …titled "Murrumbeena 3163" (the driver's fixed suburb) | **47** |

Three consequences, in order of how much they matter:

1. **It changed the product's behaviour.** Enough anonymous sign-ins to trip a
   rate limit is what surfaced S0 — the suite is now big enough to break the
   thing it is testing.
2. **Real records sit in the same tables as the debris.** Every list, count and
   dashboard the office looks at is mostly test data.
3. **The suite cannot be run whole.** 166 tests, most driving the full wizard,
   is over an hour of wall clock. It was left running during this audit and
   reached test 28 in 25 minutes before being stopped — deliberately, because
   it was still creating users.

**Fix:** tear down what a journey test creates (the `woLoop` fixtures already do
this — the customer-journey specs are the gap), delete the anonymous users a run
makes, and mark the test estimates so they can be excluded from staff lists and
swept. A dedicated Supabase project for tests is the better answer if one can be
afforded. **Size: M**

**Do not** confuse this with the suite being wrong: the specs themselves are
good, and the batch before this one caught two real bugs that unit tests missed.
It is the lack of teardown, not the testing, that has become a liability.

# NICE TO HAVE

### N1 · `app/auth/actions.ts` is the only server action without zod
Sign-up and sign-in read raw `FormData` and hand it to Supabase auth, which
validates and returns its own errors, so nothing unsafe reaches the database.
It is still the one place that does not follow the rule, and its errors are
Supabase's wording rather than ours. **Size: S**

### N2 · The daily sweep drifts an hour twice a year
`vercel.json` schedules `0 8 * * *`, and Vercel cron is UTC. That is 6pm in
Melbourne from April to October and 7pm from October to April. The code calls it
"the 6pm sweep". Same class as the hardcoded `+10:00` rule in `CLAUDE.md`, in
cron form. Either run it twice and no-op the wrong one, or accept the drift and
stop calling it 6pm. **Size: S**

### N3 · Offers only lapse when somebody opens a screen
`expire_booking_offers()` is called from the board, the portal offer list and
the offer panel — there is no scheduled sweep. This is safe, because
`respond_to_offer` re-checks `expires_at` and expires the row itself rather than
accepting a lapsed offer. Worth knowing rather than fixing: the *state* is
lazy, the *rule* is not.

### N4 · Helpers exported that nothing outside their module uses
`daysFromHours`, `customerRoomView`, `elevationsKeptBy`, `isWallLine`,
`dwTotals`, `sidesDoneCount`, `parseBlockContent`. Each is used only inside its
own file. Not dead, just a wider API surface than the module needs.

**Fixed today:** `invalidatePricingContext` was genuinely dead — exported, never
called, and its docstring instructed callers to invoke it "after writing rates
or settings", a discipline nothing followed and nothing could follow, since
rates and settings are written straight from the browser. Removed, and the
cache's comment now says plainly that the 20-second TTL is the only
invalidation.

### N5 · Two silent catches
`app/api/wo/photos/route.ts:91,110` — `.catch(() => {})` around removing an
upload that failed its magic-byte check. Deliberate and documented; the caller
already returns the real error. Listed for completeness.

# What holds up well

Worth recording, because these were the previous audit's failures:

- **The booking boundary.** `lib/validation/booking.ts` carries a comment that
  ends "If you ever find yourself adding `paymentCents` to one of these, stop."
  No action accepts an amount, every one is a single security-definer RPC, and
  the client role has no INSERT/UPDATE on `booking_offers` at all. The old C1
  and C2 are properly closed, not papered over.
- **The stage machine is mirrored, and the mirror is enforced.**
  `stages.test.ts` parses the migration and diffs it against the TypeScript
  table, so the two cannot drift silently.
- **Staleness is handled honestly.** Every booking action takes the state the
  screen believed it was in and answers `conflict` with the real one, rather
  than overwriting whatever it finds.
- **Errors say which kind of empty they are.** `loadBoard` collects per-query
  errors so an empty board caused by a failed read cannot be mistaken for a
  quiet week — the exact failure mode the RLS section of `CLAUDE.md` warns about.
- **The document is the one tree.** The tick list is an index into the
  work-order document rather than a second copy of the scope, and only real
  surfaces are tickable, so a scaffold hire can never be marked "prepped".

## Note on the full e2e run

The suite was started at the beginning of this audit and stopped at test 28 of
166, for the reason in S7. One failure had occurred by then —
`customer-journey/openings-priced.spec.ts`, hanging on page 1 of the wizard —
and chasing it down is what produced S0. Everything else that ran, passed. The
unit suite (579 tests) and the targeted specs for the last two batches were run
to completion and are green.

## Applied in this pass

- `lib/workorder/consoleData.ts` — unsigned sign-offs only; Map instead of a
  linear `find` per surface row.
- `lib/pricing/context.ts` — dead `invalidatePricingContext` removed, the
  cache's only real invalidation documented.

Nothing else was changed. The rest is written down rather than fixed, because
S1–S3 are decisions about the invoicing model, S4–S5 want a moment's thought
about where derived numbers should live, and an audit that quietly rewrites what
it is auditing is not an audit.
